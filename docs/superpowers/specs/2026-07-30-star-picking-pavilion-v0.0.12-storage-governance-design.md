# 摘星阁 v0.0.12 智能存储治理与发布设计

## 背景

摘星阁当前公开版本为 v0.0.11。应用已经把文章、分析结果、全文索引、日报、星标和情报备忘集中保存在本地 SQLite 数据库中，并通过两档保留周期自动清理过期文章。现有实现能够同步删除全文索引、修复事件簇并截断 WAL，但还存在四个长期运行后的体验缺口：

1. 「设置 → 数据维护」只显示当前数据库文件、WAL 和 SHM 的总大小，用户看不到 Electron 缓存、SQLite 可回收页、旧版数据库和迁移临时残留。
2. 删除文章会释放 SQLite 内部页供后续复用，却不会主动压缩主数据库文件；用户可能看到文件保持在历史高水位，误以为清理没有生效。
3. Electron 的网络、图片、代码、GPU 和 Dawn 缓存缺少产品级上限、占用视图和清理入口。
4. 为确保可回滚，旧 `windcatcher.db` 和旧「捕风司」目录在迁移后永久保留；当前没有安全识别、宽限期和用户确认清理流程。

本机只读审计验证了这些缺口：正式版 `%APPDATA%\摘星阁` 同时存在当前数据库、旧数据库及多类缓存；旧 `%APPDATA%\捕风司` 和项目开发 `data/` 还各有独立数据。它们并非都由当前正式版使用，但普通用户无法从界面区分。

## 目标

v0.0.12 采用「均衡智能治理」方案，在不牺牲数据安全和历史可用性的前提下：

1. 提供真实、可解释的本地占用明细。
2. 延续现有保留策略并增加低风险的 SQLite 优化与按阈值深度压缩。
3. 为可再生 Electron 缓存建立 256 MiB 软上限、自动治理和手动入口。
4. 自动清理可精确证明为迁移残留的临时文件。
5. 对已成功迁移且度过回退期的旧数据库提供显式确认清理，永不静默删除用户数据库。
6. 让采集、分析、普通清理和深度压缩互斥，失败可诊断且不破坏当前数据库。
7. 将版本号、功能文档、更新日志、发布说明、测试、安装产物和 GitHub Release 完整统一到 v0.0.12。

## 非目标

- 不改变现有用户的情报保留天数、无关内容保留天数或采集间隔。
- 不自动删除星标情报、情报备忘、设置、界面偏好、常用网址收藏或加密凭据。
- 不把旧数据库的删除授权隐含在升级、启动、普通清理或缓存清理中。
- 不把数据库拆成冷热分库，不引入云端同步、压缩归档格式或外部数据库依赖。
- 不迁移 Electron 桌面壳，不改变现有随机回环端口、Utility Process 和本地 API 安全模型。
- 不删除项目开发目录 `F:\摘星阁\data`；正式版存储治理只管理 Electron `userData` 及迁移记录明确指向的旧正式版文件。
- 不为了表面缩小缓存而关闭 GPU、禁用安全隔离或使用单进程 Chromium 参数。

## 方案比较

### 方案 A：均衡智能治理（采用）

保留当前历史策略，以可观测性、阈值治理、低频数据库压缩、缓存软上限和旧库确认清理补齐生命周期。

优点是用户几乎无需理解 SQLite，空间长期可控，且数据删除边界清晰；缺点是新增 Electron IPC、维护协调和真实文件系统测试。

### 方案 B：极致节省空间

缩短默认保留周期，并在总占用超过固定额度时提前删除非星标文章。

优点是空间上界更低；缺点是「保留 N 天」不再可信，可能在用户预期之前丢失普通历史，因此不采用。

### 方案 C：长期冷归档

把旧文章导出到压缩归档或按年度拆库，主库只保存近期内容。

优点是适合多年档案；缺点是搜索、迁移、备份和恢复链路显著复杂，超出补丁版本范围，因此不采用。

## 总体架构

存储治理分为三个边界清晰的组件：

1. **数据库维护组件**位于后端进程，只处理当前 `star-picking-pavilion.db`，负责文章保留清理、SQLite 指标、优化和深度压缩。
2. **桌面存储组件**位于 Electron 主进程，只处理当前 `userData` 下的可再生缓存、迁移临时残留和经过迁移记录证明的旧数据库候选。
3. **数据维护界面**通过现有本地 HTTP API读取数据库指标，通过受限 preload IPC 读取桌面占用并发起缓存或旧库操作；渲染层不能提交任意路径。

两类维护数据在界面聚合展示，但权限不混用：后端不能删除任意桌面文件，渲染层不能直接访问文件系统，Electron 也不直接修改正在打开的当前数据库。

## 1. 当前数据库指标

扩展后端维护快照，保留现有字段并新增：

- 当前数据库、WAL、SHM 总字节数；
- SQLite 主库已分配字节数；
- `freelist_count × page_size` 得到的可回收字节数；
- 可回收比例；
- 上次普通清理、优化和深度压缩时间；
- 当前维护状态及最近一次维护结果。

「占用空间」继续表示实际磁盘文件总和；「可回收」明确表示 SQLite 已释放但尚未返还给操作系统的主库页，避免把二者混为一谈。

## 2. 普通清理与 SQLite 优化

现有文章保留逻辑保持不变：

- 普通情报默认 180 天；
- 无关内容默认 21 天，且不超过普通保留期；
- 日报至少保留 730 天；
- 星标和情报备忘不参与自动清理；
- 单轮最多删除 20,000 条，调度器分批抽干；
- 文章与 FTS5 影子行同步删除，事件簇随后修复。

每次普通清理完成后执行 `PRAGMA optimize`。它用于更新查询规划与索引统计，不承诺缩小文件；失败只记录维护结果，不回滚已经成功提交的保留清理。

## 3. 深度压缩

深度压缩使用 SQLite 原生 `VACUUM`，不引入外部可执行文件。执行前必须同时满足：

- 当前没有采集、分析、普通清理或另一次压缩运行；
- `PRAGMA quick_check` 返回 `ok`；
- WAL 已成功执行 `wal_checkpoint(TRUNCATE)`；
- 所在卷可用空间不少于当前数据库主文件的两倍再加 64 MiB；
- 自动模式下，可回收字节不少于 64 MiB、可回收比例不少于 25%，且距上次成功压缩至少 30 天。

手动模式不受 64 MiB、25% 和 30 天阈值限制，但仍受完整性、空闲空间和互斥条件保护。压缩结束后再次执行 `quick_check`，记录压缩前后字节数、耗时和结果。

SQLite `VACUUM` 自身通过临时数据库和事务性替换保护原库。若磁盘不足、数据库繁忙、应用退出或压缩失败，原数据库保持可打开；界面显示失败原因，不把失败伪装成已释放空间。

自动压缩只在每日普通清理之后评估，不额外增加高频定时器。数据库未达到阈值时只记录「无需压缩」，不触发磁盘重写。

## 4. 维护互斥

在调度层增加统一维护协调状态：

- 采集和分析运行时，手动深度压缩返回明确的「当前繁忙，请稍后重试」，不排无限等待队列。
- 普通清理和深度压缩互斥。
- 自动压缩遇到繁忙直接跳过，下一次普通清理后再评估。
- 深度压缩运行时，不启动新的采集、分析或普通清理。
- 应用退出时等待正在执行的同步数据库步骤结束，再关闭数据库。

维护状态继续通过现有状态接口和数据维护界面暴露，不增加未经认证的本地端口或新服务。

## 5. Electron 缓存治理

受管缓存限定为当前 `userData` 下可再生的 Electron/Chromium 缓存：

- `Cache`
- `Code Cache`
- `GPUCache`
- `DawnWebGPUCache`
- `DawnGraphiteCache`

不把 `Local Storage`、`Session Storage`、`Network`、`settings.json`、`ui-preferences.json`、`credentials.v1.json` 或任何数据库算作可再生缓存。

桌面存储组件在 BrowserWindow 创建前统计受管缓存。自动清理必须同时满足：

- 受管缓存总量超过 256 MiB；
- 距上次自动缓存清理至少 7 天；
- 路径逐项解析后仍位于当前 `userData` 内；
- 目标名称精确命中固定白名单。

启动期满足阈值时删除白名单缓存目录；失败逐项记录并继续启动，不因缓存问题阻止用户访问数据。运行期手动清理先调用 Electron session 的缓存清理能力；必须在重启前处理的 GPU/Dawn 目录标记为「下次启动完成」，界面明确区分本次已释放和待重启释放。

在 Electron 初始化前设置 256 MiB 磁盘缓存软上限，限制单次运行继续扩张。软上限不等于本地总占用硬上限，界面文案不得作错误承诺。

缓存维护状态保存在版本化的 `storage-maintenance.json`，只包含时间、状态和字节数，不包含 URL、凭据、文章或搜索词。

## 6. 迁移临时残留

启动迁移前只清理满足全部条件的临时残留：

- 文件名严格匹配当前数据库迁移函数生成的 `star-picking-pavilion.db.backup-<pid>-<hex>.tmp` 及其 `-wal`、`-shm` 旁文件；
- 文件最后修改时间超过 7 天；
- 当前没有同名迁移操作；
- 解析后的文件路径仍位于当前 `userData`；
- 当前规范数据库已经存在且 `quick_check` 通过，或者整组临时数据库经检查不可作为有效规范库。

不得使用宽泛的 `*.tmp`、`*.db*` 或递归删除规则。清理结果计入「迁移残留」占用明细。

## 7. 旧数据库候选与确认清理

旧库候选只能来自两种权威来源：

1. `migration-v0.0.1.json` 中 `status: "migrated"` 的精确 `source`；
2. 兼容迁移模块已知的 `%APPDATA%\摘星阁\windcatcher.db` 和 `%APPDATA%\捕风司\windcatcher.db`。

候选必须满足：

- 当前规范数据库存在且 `quick_check` 为 `ok`；
- 迁移记录的目标与当前规范数据库一致；
- 迁移成功时间已超过 30 天；
- 候选不是当前规范数据库，也不在项目开发 `data/` 下；
- 候选文件仍是可通过 `quick_check` 的 SQLite 数据库。

界面只展示候选路径、主文件/WAL/SHM 总大小、迁移时间和是否满足清理条件。自动维护永不删除候选。

用户点击「清理旧版数据」后，由 Electron 原生确认框列出即将删除的精确数据库主文件、WAL 和 SHM。只有用户明确确认才执行；操作前重新运行全部资格检查。若旧目录中还存在设置、凭据或未知文件，只删除确认框列出的数据库三件套，绝不递归删除整个目录。空目录和可再生缓存可作为另一个明确列出的确认项处理。

删除失败按文件报告；成功后重新统计占用。已删除内容不可从应用内恢复，界面在确认框中提示先备份。

## 8. 数据维护界面

保留现有「库内情报」「占用空间」「待清理」信息，在同一卡片内增加：

- 当前数据库
- SQLite 可回收
- Electron 缓存
- 迁移临时残留
- 可确认清理的旧版数据库
- 本地总计

操作区提供四个语义独立的按钮：

1. 「立即清理」：沿用保留周期删除过期情报。
2. 「深度压缩」：回收 SQLite 主库空闲页，不改变仍保留的内容。
3. 「清理缓存」：只处理白名单内可再生缓存。
4. 「清理旧版数据」：仅在存在合格候选时启用，并进入原生确认。

每个操作都有独立的运行中、成功、跳过、待重启和失败状态。状态区域使用 `aria-live`，按钮在对应操作运行时禁用，错误信息不包含凭据或文章内容。窄屏继续使用现有响应式卡片布局，不新增横向滚动表格。

## 9. IPC 与安全边界

preload 只暴露固定方法，不接收任意文件路径：

- 获取桌面存储快照；
- 请求清理受管缓存；
- 请求清理已验证的旧库候选。

Electron 主进程忽略渲染层提供的候选路径，以自身重新扫描和生成的候选 ID 为准。所有删除前都执行 `path.resolve`、父目录约束、固定名称白名单和符号链接拒绝检查。

后端深度压缩继续走带随机令牌的现有本地 API。新增请求体只接受固定动作，不接受 SQL、数据库路径或命令参数。

## 10. 错误处理与恢复

- 指标读取失败时保留其他可用分项，并把失败分项显示为「暂不可用」，不把它当成 0。
- 自动维护失败不得阻止启动、采集、分析或退出。
- 手动操作返回稳定错误码和用户可理解的中文说明。
- 数据库完整性检查失败时禁止压缩和旧库删除，并提示先备份和诊断。
- 清理部分缓存失败时返回已释放、失败和待重启三类字节数。
- `storage-maintenance.json` 使用临时文件加原子重命名写入；损坏时回退默认状态，不删除用户数据。
- 所有维护日志只记录动作、路径类别、字节数、耗时和错误类型，不记录 API Key、文章文本、搜索词或完整访问 URL。

## 11. 测试策略

### 单元与真实 SQLite 测试

- SQLite 分配、空闲页、文件总量和可回收比例计算准确。
- 自动压缩四个阈值分别生效，手动压缩只跳过自动阈值。
- `VACUUM` 前后文章、FTS、日报、星标和备忘内容一致，文件可回收时体积下降。
- 空闲空间不足、完整性失败和繁忙状态不执行压缩。
- 普通清理后 `PRAGMA optimize` 失败不撤销已提交的数据清理。

### 桌面存储与安全测试

- 缓存白名单、256 MiB 阈值和 7 天间隔准确。
- 路径穿越、符号链接、未知目录和任意渲染层路径被拒绝。
- 临时残留只匹配精确命名且超过 7 天的文件。
- 旧库未满 30 天、迁移记录不一致、规范库不完整或开发数据目录中的文件永不成为可删除候选。
- 旧目录含未知文件时不递归删除。
- IPC schema、preload 暴露和原生确认取消路径均有覆盖。

### 界面与回归测试

- 存储分项、总计、不可用状态和四个操作状态正确渲染。
- 键盘、焦点、`aria-live`、窄屏布局和主题无回归。
- 现有保留设置、星标、情报备忘、搜索、日报、常用网址、后台驻留和自动更新全部保留。
- 正式安装包不包含测试数据库、日志、迁移样本或本机维护状态。

## 验收标准

- 用户能在一个界面理解当前数据库、可回收空间、缓存、迁移残留和旧库分别占用多少。
- 普通清理、深度压缩、缓存清理和旧库确认清理不会互相冒充。
- 自动深度压缩只在 64 MiB、25%、30 天和空闲空间条件全部满足时发生。
- 自动缓存清理只在 256 MiB、7 天和白名单条件全部满足时发生。
- 旧数据库永不自动删除；用户取消确认后文件逐字节不变。
- 星标、备忘、设置、凭据、常用网址收藏和仍在保留期内的文章在所有维护动作后保持不变。
- 任一自动维护失败都不阻止应用启动和核心情报功能。
- 本地代码、文档、版本号、标签和 GitHub Release 全部为 v0.0.12，远端安装资产完整且校验通过。
