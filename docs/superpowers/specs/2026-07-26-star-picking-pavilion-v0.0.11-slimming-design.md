# 摘星阁 v0.0.11 安全瘦身与发布设计

## 背景

摘星阁当前公开版本为 v0.0.10。产品准备继续面向同事开源，但维护者认为本地工程、安装包和运行内存观感偏重，希望在不牺牲现有能力、内置中文字体、用户数据兼容性与自动更新能力的前提下完成一次可验证的瘦身，并将当前工作区中的最新界面精修一并发布为 v0.0.11。

只读基线审计得到以下事实：

- Git 受控文件共约 250 个，总体积约 5.8 MiB；其中内置思源黑体 unicode-range 分片约 4.6 MiB。
- 本地 `dist/` 约 599 MiB，包含多个旧版本安装包与当前解包目录；`node_modules/` 约 488 MiB；`output/` 约 11 MiB，主要是测试与界面审阅截图。这些目录均已被 Git 忽略。
- v0.0.10 GitHub Release 安装包为 99,328,923 字节；现有 ASAR 约 11.9 MiB。
- ASAR 解包后约 11.6 MiB，其中界面与字体约 4.6 MiB，生产依赖约 6.8 MiB，业务代码与配置不足 0.3 MiB。依赖内可明确识别的文档、示例和测试材料不足 0.7 MiB。
- 测试数据下应用稳定启动为 Browser、GPU、Network Service、Node Utility 和 Renderer 共五个 Electron 进程，工作集约 500 MiB；渲染页面 JavaScript 堆仅约 1.8 MiB。运行内存主要是 Electron/Chromium 基线，不是业务对象堆积。
- 加入 `--disable-gpu` 的对照实验没有减少工作集，反而增加约 69 MiB，因此不能把关闭 GPU 当作瘦身手段。
- `main` 当前存在未提交的 `renderer/app.js`、`renderer/styles.css` 和 `scripts/screenshot-ux.js`。前两项是 v4 界面精修；最后一项是本次人工界面审阅使用的临时截图脚本。

## 目标

v0.0.11 在完整保留用户可见功能和数据兼容性的前提下：

1. 纳入并验证当前 v4 界面精修。
2. 删除本地旧构建、历史截图和临时审阅产物。
3. 收紧正式安装包边界，排除生产依赖中不参与运行的文档、示例和测试材料。
4. 对长信息流采用浏览器原生的离屏渲染约束，降低长时间滚动后的布局、绘制和合成压力。
5. 建立体积基线断言，防止后续版本重新膨胀。
6. 统一版本、文档、测试、声明和 Release 内容至 v0.0.11。
7. 通过受保护的 tag 工作流发布正式 GitHub Release，并核对远端资产与校验值。

## 非目标

- 不删除或降级思源黑体。
- 不删除采集、评分、聚类、日报、星标、检索、常用网址、反馈、设置、托盘或自动更新功能。
- 不迁移到 Tauri、WebView2 或其他桌面壳。
- 不把后端 Utility Process 合并进 Electron 主进程，也不使用 `--single-process`、`--disable-gpu` 等高风险 Chromium 参数。
- 不修改数据库结构、保留周期默认值或现有用户数据目录。
- 不删除本机 `node_modules/`。它是开发与发布所需的可再生依赖目录，不进入 Git 或安装包。
- 不通过宽泛的 `node_modules/**/*.ts` 或类似规则裁剪依赖源文件；这类规则节省有限，却可能破坏使用 TypeScript 源码导出的包。

## 方案比较

### 方案 A：安全瘦身（采用）

保留功能和字体，仅清理再生产物、裁剪明确无运行用途的依赖材料、优化离屏内容渲染，并用测试和包审计守住边界。

优点是风险低、兼容性强、适合补丁版本；缺点是安装包和启动内存只能获得温和改善，因为 Electron 本身占据绝大部分体积与工作集。

### 方案 B：视觉与功能裁减

删除内置字体、改用系统字体，并移除低使用率页面或后台能力。

该方案可以直接减少数 MiB，但不同电脑上的字体、排版和体验会发生变化，也违背“保留现有功能给同事开箱即用”的产品目标，因此不采用。

### 方案 C：桌面架构重构

把 Electron 替换为更轻的桌面壳，或把后端子进程改为主进程内模块、Worker Thread 或全 IPC 架构。

该方案可能降低数十 MiB 运行内存，但会同时改变进程隔离、故障恢复、SQLite 调度、自动更新和安装链路，属于独立大版本项目，不适合 v0.0.11，因此不采用。

## 详细设计

### 1. 工作区与用户改动保护

现有 `renderer/app.js` 和 `renderer/styles.css` 被视为维护者当前最新功能输入。实施前保存精确 diff 和未跟踪文件清单，任何清理都不得触及这两项改动、`data/`、本地私有配置或凭据。

由于当前改动直接存在于主工作区，实施阶段不搬运到另一个 worktree，避免复制补丁时丢失换行、编码或未跟踪上下文。发布工作使用 `codex/v0.0.11` 分支承载提交；验证后再让本地 `main` 快进到同一提交并推送。

`scripts/screenshot-ux.js` 只用于本次人工视觉验收。验收结束后删除，不纳入正式提交和安装包。

### 2. 本地垃圾清理

清理目标限定为已被 Git 忽略且可重新生成的内容：

- `dist/` 中旧版安装包、blockmap、旧 `latest.yml`、旧解包目录和构建调试文件；
- `output/` 中历史 Playwright、布局审计和 UX 审阅截图；
- 本次使用完毕的临时截图脚本。

以下内容明确保留：

- `data/` 下所有数据库、WAL、SHM、设置和界面偏好；
- `node_modules/`；
- `.claude/`、`.superpowers/` 与 `.worktrees/` 中的用户或工具状态；
- Git 受控的历史设计、实施计划与发布文档。

正式构建前清空 `dist/`，确保 v0.0.11 产物目录中不混入旧版本文件。正式验证结束后，仅保留 v0.0.11 Release 所需资产；`win-unpacked/` 可在装机版烟测完成后删除。

### 3. 安装包边界收紧

保持 electron-builder 现有应用文件白名单，在其基础上只排除已确认不参与运行的生产依赖材料：

- 依赖包内的 `docs/`、`doc/`；
- `example/`、`examples/`；
- `test/`、`tests/`、`__tests__/`；
- Markdown 说明文件和 source map。

许可证义务不依赖这些散落文件：`THIRD_PARTY_NOTICES.txt` 继续由锁文件和依赖许可证生成，并作为安装资源与 Release 资产发布。依赖的 `package.json`、运行时 JavaScript、JSON、字符映射表与其他数据文件必须保留。

包审计脚本增加可回归的体积预算：

- ASAR 上限由宽松的 18 MiB 收紧到基于当前实测、仍留有迭代余量的 13 MiB，且 v0.0.11 候选 ASAR 不得大于当前基线 12,476,662 字节；
- 安装包上限由 120 MiB 收紧到 100 MiB；
- v0.0.11 候选包必须不大于 v0.0.10 的 99,328,923 字节；
- 包内继续禁止数据库、日志、截图、文档、测试、开发依赖和秘密。

如果排除规则造成任何依赖缺失，装机版启动烟测会失败；此时回退具体规则，而不是抬高风险或跳过验证。

### 4. 运行时内存策略

不以一次进程私有字节快照作为成功标准。GPU 进程会根据驱动和纹理分配产生较大波动，工作集与真实长列表场景更有参考价值。

前端信息流维持现有每页 30 条与按需加载逻辑，并为离屏时间线分组、卡片或等价稳定容器增加 `content-visibility: auto` 与合理的 `contain-intrinsic-size`。浏览器仍保留完整 DOM 和交互语义，但无需持续布局、绘制远离视口的内容。

该优化必须满足：

- 当前视口卡片立即可见；
- “加载更多”、回滚、星标、复制、搜索和视图切换不受影响；
- 800×600 至 1920×1080、四档缩放和深浅主题不出现滚动跳跃或横向溢出；
- `prefers-reduced-motion` 行为继续有效；
- 启动工作集不显著回退，长列表场景的渲染器工作集或绘制负担有可重复改善。

不会为了追求数字而关闭 GPU、关闭沙箱、合并进程或限制 V8 堆上限。

### 5. v4 界面精修纳入

保留维护者现有界面改动：

- 卡片按领域使用左缘色条；
- 元信息减少重复领域标签；
- 评分胶囊弱化为辅助信息；
- 卡片缩略图使用异步解码；
- 日报区块内联间距迁移到样式类；
- 深浅主题的玻璃层、卡片层、导航、筛选与操作按钮层级重新收敛；
- 氛围层降噪，现有交互和状态逻辑保持不变。

实现时修正格式问题并补足回归断言，不改变这些产品判断。

### 6. 测试与验证

实施采用测试先行：

1. 更新版本一致性测试，使旧的 v0.0.10 断言先失败。
2. 为 v4 卡片领域属性、异步图片解码和日报样式类补充渲染集成断言。
3. 为打包排除规则和收紧后的体积预算补充包审计测试。
4. 为离屏渲染 CSS 增加静态约束测试，并通过真实 Electron 布局矩阵验证。
5. 运行完整单元/集成测试、真实 Electron 测试、生产依赖审计、第三方声明一致性检查、版本检查和严格信源审计。
6. 从空 `dist/` 构建一次候选包，运行包边界与产物版本验证。
7. 启动 `win-unpacked` 版本，验证安装包同源代码可启动、页面可加载、主要视图可切换并能正常退出。
8. 记录 v0.0.10 与 v0.0.11 的 ASAR、安装包、Release 资产和内存基线对比。

外部信源严格审计依赖实时网络。若某个网站短时不可用，必须如实记录具体信源与错误；不能把它伪装成产品回归，也不能跳过其余本地验证。

### 7. 版本与文档

统一更新以下内容到 v0.0.11：

- `package.json` 与 `package-lock.json`；
- 版本与品牌测试；
- `README.md` 的下载、校验、版本亮点和开发命令；
- `CHANGELOG.md`；
- `RELEASE_NOTES.md`；
- `RELEASING.md`；
- `THIRD_PARTY_NOTICES.txt`；
- GitHub Release 标题、正文和六项标准资产。

Release Notes 必须明确说明：

- 完整保留功能和数据；
- v4 界面精修；
- 清理与包边界收紧；
- 运行内存优化的真实边界；
- 安装包未签名与 SmartScreen 提示；
- 升级与回滚兼容性。

### 8. 提交与发布

提交按可审阅边界拆分：

1. 设计与实施计划；
2. 回归测试；
3. 界面精修与离屏渲染；
4. 打包边界与清理；
5. v0.0.11 版本和发布文档。

完整验证通过后：

1. 确认最终 diff 仅包含本次范围；
2. 将本地 `main` 快进到候选提交；
3. 推送 `main` 到 `origin`；
4. 创建并推送带注释的 `v0.0.11` tag；
5. 等待 GitHub Actions 的 release workflow 完成；
6. 核对 Release 为非草稿、非预发布，六项资产齐全；
7. 下载远端 `SHA256SUMS.txt` 并核对安装包 digest；
8. 不覆盖或强推已公开的 Release。

## 错误处理与回退

- 清理前精确列出目标；只删除已验证位于 `dist/`、`output/` 或明确临时路径下的文件。
- 若工作区出现非本次新增的未知改动，停止合并与发布，保留现场。
- 若依赖裁剪破坏装机版启动，撤销最小的裁剪规则并重新构建。
- 若测试、审计、构建或版本验证失败，不创建 tag。
- 若 tag 工作流失败且尚未产生公开 Release，可在核对精确目标后修复并发布更高补丁版本；若 v0.0.11 已公开，则不复用 tag。
- 用户数据库、设置与凭据在整个流程中均不迁移、不清空、不纳入 Git。

## 验收标准

- 当前 v4 界面精修完整进入 v0.0.11。
- 所有用户功能、数据库和设置兼容性保持不变。
- 本地旧版 `dist` 与历史 `output` 产物被清理，用户数据和开发依赖保留。
- ASAR 小于 13 MiB且不大于当前基线 12,476,662 字节；安装包小于 100 MiB且不大于 v0.0.10 的 99,328,923 字节。
- 完整本地验证矩阵通过；实时信源审计结果单独如实报告。
- `main`、`package.json`、锁文件、文档、tag、安装包、`latest.yml` 和 GitHub Release 均一致为 v0.0.11。
- GitHub Release 六项标准资产齐全且 SHA-256 校验一致。
