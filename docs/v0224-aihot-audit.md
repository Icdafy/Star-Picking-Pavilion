# AIHOT 升级脉络与摘星阁 v0.2.24 深度对照

> 研究时间：2026-10-07（北京时间）｜研究对象：AIHOT 开源框架与摘星阁桌面实现｜方法：提交历史纵向追踪、当前代码横向对照、问题先复现再修复

本次研究固定 AIHOT `main` 的提交为 `852dd145df873d080eeebe0fd986f321f19ae326`。摘星阁上次独立的上游整合记录截至 `885b736dc0fd3ef3d4c9c70af2bc3a981a99ff38`；两者之间有 **56 个新增提交**。摘星阁本次开发起点为 v0.2.23 的 `91b6af4`，研究对象包括它此后已自行完善的来源、日期、调度和桌面功能，不把旧审计里的“未支持”直接当成今天的缺口。

此次适配的主要收益是让原文、模型判断和事件综述保持可信：保住纯文本型号，清除隐藏噪声，避免未知模型收到图片和同名端点误用回执，让模型漏答与生成失败可以恢复，让材料更正影响综述，并使评测如实披露失败。没有新增运行依赖，保持 Electron、SQLite、本机数据与双行业定位。

## 一、两个项目的关系，以及此次研究怎样作判断

AIHOT 的公开定位是一个能够持续采集信源、筛选行业新闻、归组热点并生成日报的网站框架。摘星阁把同样的核心流程放在 Windows 桌面，行业固定为低空经济与商业航天，并扩展公司、融资、投资关注、情报日志、归档和本机模型设置。它们共享产品思路，却已经采用不同的运行条件。

这种区别决定了“复制”的具体含义。一个 SQL 修复只能在存在同样的表和查询时复制；一个有关原文语义的修复，即使程序语言、数据库和界面完全不同，也值得适配。判断的单位应是用户实际看到的行为：原文中写着什么、模型拿到什么、失败以后有没有重试、事件列表和综述有没有一起更新。不能只数搬进来的文件数量。

本次首先把上游仓库拉到本地，读取固定提交的完整历史和关键差异；再对照摘星阁同一条链路的实现。两份只读研究分别整理版本脉络和本地缺口，随后通过最小输入验证。明确的问题先加入回归，让旧代码失败，再修到通过。所有自动验证都使用隔离配置或本地模拟端点，没有读取用户密钥来进行付费评测。

报告的来源主要是公开仓库的提交与源文件。提交说明提供线索，最终仍以代码和可复现结果作判断。对作者的私人背景、主站实际流量、真实调用成本和模型效果，没有足够的一手信息，本文不作推断。上游测试通过也不能替代摘星阁自己的验证。

## 二、纵向研究：从开源框架到持续导出的线上引擎

### 1. 9 月 29 日：行业框架的第一条公开代码线

AIHOT 当前 Git 历史最早的提交是 `877d6d5`，说明为 “AIHOT: the open-source framework”，日期为 2026-09-29。这是公开仓库代码线的起点，不等于产品从这一天才开始存在。它已经包含采集、精选、事件、报告和公开读取的主要结构，后续更新是在这套结构上连续修复和重组。

早期几次修复很能说明新闻系统的难点。`de4be99` 把没有时区的来源日期按信源时区读取，解决同一段文本在 UTC 与北京时间机器上相差八小时的问题。`de46b70` 处理资料晚到、晚完成归组后漏入报告的问题。`1db4b16` 保留 Atom XHTML 混合文字的顺序。这些问题没有改变应用的页面数量，却直接改变了读者拿到的信息。

摘星阁 v0.2.2 的上游审计已经适配了这批修复，并使用自己的 SQLite、采集器和报告窗口实现。它还保留 MIT 许可与原项目署名。因此这次研究从 `885b736` 以后开始，并同时查看此前适配是否有边界未覆盖，而不是重做一次初始移植。

### 2. 9 月 30 日至 10 月 2 日：从“能生成”走向“失败可恢复”

`c3ba0ca`、`8d5a39b`、`035f7b7` 等更新处理卡住的模型步骤、来源采集和公开内容的一致性。`ddf1c19`、`b5e2a09` 进一步把付费向量和 X 搜索结果的回执与业务提交结合。核心矛盾是：远程调用已经付了钱，进程却可能在结果写入前退出；如果重启后简单重跑，既重复收费，也可能生成另一份不一致的结论。

摘星阁已有有效结果回执、预算原子占用、执行中的共享请求和整轮任务协调。它没有付费 X 搜索或向量采集，所以不需要照搬这两条渠道的数据库事务。但同样的原则适用于普通模型：只有确定属于当前提供商、当前输入的答复才可以复用。代码对照暴露出本地回执只绑定模型 ID，切换同名端点时仍会使用原端点结果。v0.2.24 为所有相关回执加入实际路由身份。

这个阶段的 `3343fe2` 还改善事件进展的时间阅读。它提醒我们，事件归组之后仍要保留每一篇报道的时间和事实；一个故事包含旧阶段与新阶段，并不代表所有报道都相互矛盾。摘星阁本次修复了旧进展日期否决当前重复报道的问题，并把报道时间加入综述证据。

### 3. 10 月 3 日：成刊纪律与 4.0 引擎边界

`5794327` 将主站的精选与成刊规则带入开源仓库。评分之后继续判断具体新信息，按新闻事实保留代表，日报考虑前七期，同一个事件只有新增事实才继续出现，同一来源的正文数量也受约束。这一变化很重要：一条新闻分数高，并不自动代表读者需要连续七天反复看到它。

但这套规则还依赖上游事实分组、公开代表席位和日报刊物结构。摘星阁的周报、月报按文章的采集及归组窗口汇编，用户还可以检索、收藏所有已收录资料。把上游“每个事实一个席位”直接套在本地全部动态上，会改变历史完整性；把周月报简单改成日报拼接，也会改变已有研究记录的口径。本次记录这个可学习方向，保持原有报告语义，先处理可以证明确有错误的归组和综述环节。

随后 `1ca5d6d` 发布 4.0 的引擎组织方式：开源引擎直接从线上代码导出，模型榜、Codex 重置监控和主题大事记移出通用框架。这里的关键不是“增加三个功能”，而是让通用能力与站点专属能力分开维护。摘星阁原本没有这些主站运营模块，复制它们的删除动作没有实际意义。

`d5d9645` 进一步把站点身份放入 `site/`，行业规则留在 `industry/`，扩展能力放进 `modules/`。摘星阁已经有 `config/industry/` 和统一品牌配置。后续若支持更多行业，可以沿这个方向独立行业包；当前不需要为了目录外观一致而搬动整仓。

### 4. 10 月 4 日：原文、日期与公开更正成为共同约束

`ec42ff7` 把更正和撤回的影响统一传递到页面、接口、报告和分享内容。`fd51bcf` 让事件概览答案先行，并把同一份生产输入用于综述评测。`561b880` 提供受材料版本约束的历史日期纠正。它们的共同问题是：一个结果生成出来之后，原文和材料仍会变化，缓存不能成为另一份永远不更新的事实。

摘星阁的综述提示词早已要求第一句交代主体、动作和结果，这一点不需要重复移植。真正的差距在运行条件：原来只在报道数量变化时重写，材料同数更正不触发；失败却把数量记成已完成；返回模型后也没有重查证据。这些都是确定的代码行为，v0.2.24 用材料指纹、严格答复校验和异步写回检查修复。

`309e32e` 同时修复 Atom 纯文本、英文日期的夏令时和坏 JSON 日期。纯文本不是 HTML：原文写着 `<model>`，不应该被去标签工具删除；原文写着一段 `<img>` 字面示例，也不应该转成图片请求。日期没有自带时区时，必须按来源偏移解释，不应该先受服务器夏令时规则挪动一次再换算。这几项本地仍有明确缺口，全部纳入本次适配。

### 5. 10 月 5 日至 10 月 7 日：读取效率与细节正确性

这一阶段出现页面复用、按需正文读取、图片传输和 MCP 订阅共享。对在线网站而言，订阅连接、缓存字节和发布排空有明确的资源收益；本地 SQLite 同步查询和 Electron 页面没有相同的连接模型，所以不需要安装同样的服务设施。摘星阁已有的执行中请求 Map 会在成功或失败后释放，与 `175d230` 的共享边界一致。

直接可适配的细节包括 `1756ad7` 的视频播放／嵌入地址识别，`337e7e1` 的明确视觉能力判断，`c45cf68` 的隐藏正文处理，`e6cda05`、`7d6ac83` 的引号属性扫描，以及 `672e2c1` 的评测失败口径。它们看起来小，却在采集或每次模型调用上重复发生，累积影响很大。

最新 `852dd14` 修复候选事件的报道计数：PostgreSQL 子查询的内层别名遮蔽了外层文章，导致读取了错误的最新分析。摘星阁没有上游的 `analyses/fact_articles` 历史结构，直接读取文章当前分析字段，没有这条同名错误。本文明确区分“已经审阅并确认无对应问题”与“复制了该 SQL 修复”。

从读者视角看，最需要同步的不是表格右侧的功能数量，而是同一条材料进入系统时的行为。本次分别跟踪输入、入库、分析、归组、综述和评测，下面给出每处问题的实际触发条件与修复边界。

### 1. 原文保真：类型信息要穿过整条清洗链

旧 Atom 采集把所有标题、摘要和正文都送进 HTML 清洗。`<title type="text">&lt;型号&gt;</title>` 会得到空标题；纯文本正文中的 `&lt;img src="…"&gt;` 会生成伪图片。只修采集还不够，入库 `structureItem` 和后续清洗会再次删掉尖括号。

现在采集器在 XML 解析时保留文本构造类型。默认和 `text` 的值已经经过 XML 解码，不再解释成 HTML，也不会再把 `&amp;` 字面值解码一次。HTML 和 XHTML 继续清洗；XHTML 保留整个根 div 后交共享扫描器去标签，避免根属性里的大于号残留。适配器返回明确的纯文本格式，入库保持这个语义。

本地清洗版本从 1 升到 2。已经按 v1 清洗的内容按纯文本复查，早期未清洗的内容仍按原 HTML 规则处理。启发式摘要也不再重复去标签。这个设计没有新增必填数据库字段，现有分析和星标无需重建。过去已经丢失的原文字符无法凭空恢复，本版不会根据猜测补造旧标题。

复核同时补齐四个边界：CDATA 里的裸 ampersand 不再被 XML 修补器改变；空摘要回退正文；XML Base 按实际选中的 alternate 链接解析；没有原文地址的条目保持空地址，由既有入库守卫拒绝，不能生成 `/undefined`。回归不仅检查返回字符串，也检查最终入库和后台分析后的结果。

### 2. HTML 清洗：一个大于号不能改变事实

输入 `<a title="型号 > 参数">商业航天完成首飞</a>`，旧正则会在属性里的第一个 `>` 结束，把 `参数">` 残留到标题中。较长的属性还可能超出去标签正则的长度上限，整段标记保留下来。这会污染检索、相似度与模型输入。

v0.2.24 适配 AIHOT 的引号感知扫描器，区分标签名、属性名、引号值和无引号值。双引号、单引号以及无引号值中的撇号都不会误配；标签之间仍按调用场景保留空格或直接拼接。RSS、规范化、JSON API 与模型分隔共用这份实现，避免同一个错误在四个入口重复修四次。

模型分隔还有一个独立约束：外部文字可能在普通 HTML 属性内写 `</item><candidate>`。即使外层标签保留，这些字面标记对模型仍可见。因此先正确识别顶层分隔标签，再把剩余数据中的分隔前缀失活。正文仍是外部数据，已有安全提示词继续生效，不能因清洗通过就把它提升为可信指令。

### 3. 正文证据：屏幕上隐藏的广告不该进入研判

旧正文提取只移除脚本、导航等元素，`display:none`、`visibility:hidden` 或 `hidden` 内的文字与图片仍会被读取。实际复现中，隐藏广告和谣言出现在模型将要阅读的正文里。若这些内容带日期、投资额或公司名称，它们还可能改变后续事件和融资判断。

本版处理直接声明的隐藏属性，并解析内联 display、visibility 的声明优先级：属性名与值不分大小写，important 优先，否则后写覆盖；无效声明不会把原先隐藏的内容变成可见。解析会跳过样式字符串与括号里的分号，避免把背景 data URL 中的 `display:none` 误当真正的声明。

惰性图片常把不可见的占位图放在 noscript 真图旁边。本版保留备用真图，移除隐藏占位图和备用导航文字。RSS 封面优先使用实际提取出的可见图片，避免正文清干净了，封面却还来自隐藏占位图。该实现不执行脚本、不加载远程样式，也不宣称等价于完整浏览器的外部 CSS 计算。

YouTube、youtu.be、Vimeo 的播放、短视频、嵌入和分享页沿用上游明确地址规则，不能作为新闻正文或图片候选。普通新闻仍可带有关视频的事实摘要；页面没有可核实正文时不把推荐视频和评论假装成文章。

### 4. 日期：来源墙钟与机器时钟不能混在一起

英文 “March 8, 2026 02:30 AM” 没有时区。在纽约系统上，这一天的 02:30 落入夏令时切换缺口，直接让本机 Date 解析会推进到 03:30；之后再按北京时间组装，资料被无端移动一小时。本版先在 UTC 中读出英文墙钟字段，再放进来源偏移。回归在 UTC、上海、纽约与柏林四个系统时区下得到同一结果。

原文自带 PDT、EST、GMT 等明确时区时，按它自己的时区读。CST 在中文来源中含义不稳定，不采用 JavaScript 默认的美国中部解释，按来源偏移读取。非法英文日历如 February 30 返回无日期。现有年月、月日精度和缺日期说明继续保留，本版没有改变 v0.2.23 的新闻时间轴口径。

JSON 来源中日期可能是坏字符串、对象或超范围数字。原来东财适配直接调用 replace 和 toISOString，单个坏日期可以终止整批。现在日期无法转换时记为未知，后续条目照常处理；交易所和电报的日期路径也限制无效日历与超范围时间。未知日期不应被猜成今天。

### 5. 模型：能力声明与路由身份都属于事实

旧实现把“没有声明输入类型”视为可能支持图片，并在图片调用失败后降级。这种默认探测对用户手工添加的文本模型会增加下载和无效请求。现在只有明确包含 `image` 的模型才走图片理解。未知或文本模型仍可正常预筛、评分、理解与写作，不需要为了继续使用它而补一个假的视觉能力。

设置页同时显示文本模式，未声明时图片复选框不勾选，并说明确认支持后可以勾选。默认内置视觉模型已有明确声明，所以正常图片分析继续工作。真实 Electron 验证检查了未声明模型的说明、复选框和原文尖括号的安全显示。

更隐蔽的问题是回执身份。同一个模型 ID 在两个提供商或两个网关里可以指向不同服务。旧代码用模型 ID、提示词和输入作键，切换端点可能拿到前一个服务的结论。现在身份包含提供商、协议、规范化端点和模型 ID，不包含 API Key。密钥轮换不会改变同一服务的内容身份，路由变化则使用另一组回执。预筛、独立评分、理解、翻译、归组、综述与报告导语共同使用这项规则。

本地模拟两个同名端点，分别返回低分和高分，实际验证调用次数为各一次；原路由重复请求复用。这个测试证明路由隔离，不代表比较了任何真实模型的质量。

### 6. 归组：漏答不是“不同事件”，旧日期不是全事件否决票

旧 `normalizeJudgement` 先给所有候选填 different，然后逐个覆盖模型答复。模型返回空数组、缺项、重复编号或非法关系时，剩下的 different 看起来像有效判断，还可以落回执。现在要求每个候选恰好出现一次，关系合法且置信度为有限的 0—1 数值；错误答复抛出解析失败，资料保持待处理。新版回执键也隔开旧的宽松结果。

第二个问题发生在召回池。一个故事里已有 10 月 1 日旧进展和 10 月 6 日新进展，新稿完全重复 10 月 6 日；旧实现只要遍历到任何日期冲突成员，就把整个故事设为不相容。现在相容性绑定具体证据，优先选相容的精确事件键，再比较相似度。10 月 1 日资料不再否决 10 月 6 日的重复报道，只有旧进展可用时仍保持冲突，防止跨批次自动归并。

这不是把所有同公司消息合在一起。主体、动作、型号、时间和状态仍承担原有约束，灰区继续交模型及独立复核。复现与回归同时覆盖正确匹配和真正冲突，不通过放松门槛来制造更多合并。

### 7. 综述：当前材料决定当前答复

原来综述只看报道数量是否变化。同样三篇报道，其中一篇把“已经完成”更正为“尚在计划”，数量仍是三，综述不重写。模型调用失败后又把 digest_size 写成三，下一轮同样不再重试。还有一种形状错误：答复是空对象，未经严格检查可能写入文字 undefined，再配上完成指纹，永久阻止恢复。

本版使用所有相关成员的 ID、当前标题摘要、来源与报道时间构造指纹，包含提示词和实际模型路由。进入综述的证据按报道时间先后排列，采用最新八篇；指纹仍覆盖全部成员，因此窗口外材料更正或撤回也会使旧综述失效。没有可信发布时间时明确写未确认，不能用它推断事件发生日期。

材料发生变化时先清除陈旧综述，再请求新答复；不足最低报道数量时不再生成。模型失败、空对象、数字和空白文本都不写成功状态。返回之后重读指纹，期间材料变化则保存已付费回执但丢弃旧写回，下一轮用新材料继续。这避免了异步调用完成得慢时，把更正后的资料覆盖回旧事实。

`clusters` 只新增一个可空 digest_hash 列；旧库可增量升级。撤回材料不再支撑综述或成员刷新，原始文章和星标仍保留。现有最近三天活跃事件窗口和每轮调用上限继续使用，历史事件专项重写界面并未在此次新增。

### 8. 评测：一个正确答复不能掩盖九次失败

旧关系评测准确率只除以成功预测数量。如果十对样本只成功一对且答对，准确率会显示 100%。这是一个有定义的条件准确率，但如果不同时展示覆盖率，读者很容易把它当成整组效果。本版保留这个统计口径，同时新增成功覆盖率和把所有失败计入分母的完整准确率。

例如两对样本，一对正确、一对失败：成功准确率为 1，覆盖率为 0.5，完整准确率为 0.5。关系指标和合并门槛指标都使用总样本数，JSON 与 Markdown 同时披露；全部失败时完整准确率与覆盖率为零，错误数量保持完整。

同一轮中多个金标可以包含相同报道对。评测按实际模型输入共享 Promise，成功或失败只请求一次，但每份金标仍独立计分。共享失败只限这一次评测，线上执行中的请求仍在完成后释放，避免把临时网络失败永久缓存为模型结论。未经真实标注集与模型调用，本次不声称行业精度上升多少个百分点。

## 四、横纵交汇：哪些值得复制，哪些需要继续独立设计

### 1. 已经同步的业务原则

从历史上看，上游先解决管线完整性，然后引入内容版本和公开一致性，再把影响付费调用的细节修到采集和模型输入。摘星阁继承了管线，却保留了自己的适配器与回执规则，许多缺口恰好出现在这条边界上。因此此次把共享规则放在最小公共模块里：文本扫描共用、模型身份共用、综述输入与失效判断共用。后续再增加来源或模型时，不必逐入口重新发现同一个问题。

这次最容易被低估的收益是失败状态保持真实。漏答、空正文、临时请求失败、无效综述和预算熔断不是同一种业务结果。把它们提前写成“已处理”会让应用表面安静，却失去下一轮恢复的机会。此次改动把模型漏答与综述失败留在待处理路径，把未知输入能力明确设为文本模式，把评测失败显式纳入报告。

同样重要的是升级保留。数据清洗只对需要更新的记录处理；归组、综述和视图不清空原始文章；密钥不进入研究资料或回执身份；MIT 来源署名继续随安装包提供。新增能力没有要求用户重建数据库或重新配置所有模型。

### 2. 暂未整体复制的能力及原因

上游 3.0 的事实代表席位和成刊纪律值得继续学习，但需要先定义摘星阁的日报用途。若日报用于快速读完昨日重点，来源均衡与前期记忆有意义；若它还承担投研归档，压掉已报事件可能遗漏后续证据。本版保持完整资料入口，记录这项设计方向，不能用“已同步核心修复”暗示整套成刊规则已等价。

更正／撤回管理界面、手工锁定归组、历史日期批量纠正和专项综述评测也需要完整的材料版本与操作审计。仅增加按钮而没有预览、版本检查与撤销路径，不足以复制上游的可靠性。当前本地已经有自动日期补查与事件字段修复，此次没有再引入一个未经设计的人工批量改写入口。

MCP、公开 RSS、分享图、IndexNow、飞书通知与云端运营模块依赖公开站点身份、连接管理、访问控制或第三方账户。用户此次授权升级并发布桌面版，不需要自动接入新账户或向外部服务发送情报。本版保留本机鉴权 API 和原有导出方式，没有为迁就上游目录结构增加服务器部署负担。

X 空原帖、纯链接推文与付费补读的特殊处理同样不能套到所有导入。摘星阁没有 X 原帖数据结构，外部导入仍要求明确标题与原文地址。如果以后支持纯链接待补读，应先提供可见的未确认状态和来源审计，不能凭一个地址购买并展示虚构摘要。

最新报道计数 SQL 修复已经审阅，没有相同的本地查询错误。更广的 single/composite/unknown 内容范围区分是另一项待设计能力；多事件文章不必然是盘点，一篇融资加首飞也可能有完整主线，所以不能用事件数量简单代替范围判断。

### 3. 后续三个有条件的方向

最可能的方向是继续沿当前桌面架构改进事实与报告质量：先有真实的行业标注集，再评新闻事实重复、来源代表和摘要约束，保持全部动态与星标完整。这样上游的成刊纪律能够逐条适配，并且每次都有可回放的证据。

风险最大的方向是逐版本照抄网页架构与数据库迁移，同时仍保留旧桌面入口和旧报告口径。短期会多出一些菜单，长期却需要维护两套内容身份与失效规则，最后难以回答哪一份才是当前事实。这里的风险判断来自现有架构差异，不是对上游实现的否定。

更乐观的方向是把双行业知识整理成稳定行业包，用一个清晰的材料版本体系支持桌面、本机 API 与未来新增出口；原文、评分、归组、综述和刊物共同消费同一份事实状态。要走到这一步，需要独立设计迁移、审计和标注评测，不能靠此次修复宣称已经完成。
