# v0.2.20 后端审查与改进

基线为 main 的 `d74a145`（v0.2.19），本轮从真实桌面产品的运行边界检查 server 全部子系统及对应桌面交互。先运行原有 913 项测试，再针对有具体触发条件的问题增加回归；既有安全边界、数据语义和发布门禁保持。本文记录已观察到的故障与修复，不代表对所有输入和环境的形式化证明。

## 有实际影响的问题

| 触发条件 | v0.2.19 的行为 | v0.2.20 的行为与证据 |
| --- | --- | --- |
| 重复手动采集，或最终归组尚在途 | 两次任务可分别进入尾部；分析锁释放后 running／退出等待忽略剩余工作。 | 同一整轮 Promise 去重，持有整轮状态；定时器和维护协调，退出等待尾部。backend-lifecycle 的门控并发测试覆盖。 |
| 修改采集间隔 | 设置已落盘，旧 setInterval 仍按旧间隔运行。 | 保存成功后替换两个循环，保持单套计时器，不重新安排启动采集；状态接口公开有效间隔。 |
| 两次评分／内容理解中的一个先失败 | Promise.all 提前返回，其他付费请求仍执行和写回执。 | settleAll 等待所有分支，再传播错误；真实本地模型桩复现并核对剩余请求完成时刻。 |
| 同一 RSS 批次后续文章或 FTS 写入失败 | 前面已提交的文章留下，成功计数没有同步，重试看到半批。 | 文章、FTS 与成功计数共用事务；第二条插入触发失败时整批回滚，重试完整写入。 |
| 采集响应回来前停用、移除或改写源 | 旧地址响应继续入库，并覆盖新配置的健康状态。 | 写入前重新读取启用／移除／URL／类型／选择器；不一致则跳过，失败记账也受同一配置条件约束。 |
| 相同模型输入并发请求 | 两个请求在回执尚未出现时各占一次额度并付费。 | 按原回执键共享在途调用；成功后继续持久复用，失败清理在途状态，可重试。 |
| 日额度写入失败、或日期补提取运行 | 小时扣减可能单独提交；日期补提取未先占调用额度。 | 两种额度原子提交；补提取先 reserveCall，熔断恢复尝试次数与原退避字段，继续待处理。 |
| 服务返回长 Retry-After | 整体超时触发后仍等完整退避时长，测试桩还能继续请求。 | 退避使用可中断定时器；两个模型协议的一秒截止均能中断三十秒等待。 |
| 模型服务返回重定向 | 特别是 Anthropic 自定义鉴权头可能随跳转请求发送。 | 三种调用入口使用 redirect:error；两台真实回环 HTTP 服务证明目标端未收到请求。 |
| 错误响应、声明超大或非法最终地址 | 未读 body 在抛错后留下连接。 | 主动取消未读 body；流式超大通过迭代器取消并释放 reader；连接清理测试覆盖。 |
| 超过 500 条匹配，再筛选领域／精选／星标 | 提前选出任意 500 条，较新的可见结果可能一个都没有；词库同时少计。 | 完整子查询过滤后排序和分页；560 条样本中保留最后 50 条可见记录，首／次页 30／20，词库为 50。 |
| 后台导语写作期间用户重新生成报告 | 原整份 content_json 覆盖用户的新快照。 | UPDATE 同时比较原 content_json；日报、当前／上周周报、月报四个位置均保留新版，只有实际成功回填计数。 |

在隔离目录还原基线并放入同一回归用例，14 个针对原缺陷的场景全部失败；当前实现均通过。源代码隔离副本、原始失败、最终复现和本轮日志保存在 work/v0220。第一轮复现中，失败断言位于释放测试门控之前，导致旧代码夹具的未完成调用未释放；修正夹具释放顺序后完成 14 项确定性复现，产品断言未放宽。

## 成熟项目与官方资料如何落地

- [Miniflux worker](https://github.com/miniflux/v2/blob/main/internal/worker/worker.go)：观察工作池接收任务、停止与完成计数的生命周期。摘星阁采用整轮状态和完整等待，保持本机四个采集 worker。
- [BullMQ 去重](https://docs.bullmq.io/guide/jobs/deduplication)：参考任务未结束期间按身份抑制重复工作的原则，落为整轮 Promise 与回执键在途 Map；本机单服务无需引入 Redis。
- [Undici 连接资源说明](https://github.com/nodejs/undici/blob/main/README.md#garbage-collection)：请求失败时消费或取消响应正文，落为统一 cancelBody 与已有有界读取。
- [SQLite 事务](https://www.sqlite.org/lang_transaction.html)：对原子性和写事务边界核验，落为现有 BEGIN IMMEDIATE／SAVEPOINT 助手管理批次和双额度写入。
- [SQLite FTS5](https://www.sqlite.org/fts5.html#the_trigram_tokenizer)：使用 trigram MATCH 与存储内容的 LIKE 条件，分页在完整命中集之后执行，保持短词覆盖范围一致。

以上为独立实现的设计参考，没有复制第三方代码、引入服务或变更项目许可证。

## 产品边界与后续观察

自动出刊仍是本地定时任务，没有承诺关机期间持续采集；重新生成及归档仍由既有功能处理。关闭时的桌面进程超时兜底保持，长外部请求可能触发强制终止，因此不能将整轮等待误读为任意网络条件下都能优雅完成。

实网信源的站点改版、限流、拒绝访问和零结果属于依赖外部服务的运行结果，应保留本轮严格采集实测；不能用单元测试或一次成功宣称 186 个源永久可用。数十万行保留清理的同步工作量、历史迁移耗时与更大数据库的词库计数成本，可在后续真实运行数据支持下继续优化。两万行合成样本的检索约 22–29 毫秒，但词库首次完整计数约 3.2 秒、缓存约 1 毫秒，首次计算仍会占用本地事件循环；这一成本未消除，见验证记录。本版先处理可复现的缺陷，未为桌面单用户产品扩建分布式后端。
